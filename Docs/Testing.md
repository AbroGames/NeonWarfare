# Тестирование

[← README проекта](../README.md)

Тесты живут в отдельном проекте `Tests/NeonWarfare.Tests`, фреймворк — **xUnit v3**. Запуск:

```bash
dotnet test                                              # все тесты
dotnet test --filter FullyQualifiedName~DocsLinksTests   # один класс
```

В Rider тесты видны как обычно: тестовый проект входит в `NeonWarfare.sln`.

## Принципы

* **Только юнит-тесты.** Godot из тестов не запускается: ни движок, ни сцены, ни ноды. Поэтому
  тестовый проект собран обычным `Microsoft.NET.Sdk` и **не ссылается** на `NeonWarfare.csproj` —
  ссылка затянула бы `GodotSharp`, который вне процесса Godot не инициализируется.
* Отсюда следует, что тестировать можно ровно две вещи: **чистую логику** (классы, не зависящие от
  движка) и **инварианты репозитория** (структура файлов, документация, локали, соглашения).
  Всё, что живёт внутри дерева нод, по-прежнему проверяется сборкой и ручным запуском игры — см.
  [Быстрый старт](Quick-start.md).
* **Тест собирает все нарушения и печатает их одним списком**, а не падает на первом. Иначе
  документацию приходится чинить итерациями. Для этого есть `Infrastructure/FailureReport`.
* Проверка, которая разбирается по файлам, оформляется как `[Theory]` с одним файлом на случай —
  тогда в отчёте видно, какой именно файл сломан.

## Соглашения

* Расположение: `Tests/NeonWarfare.Tests/<Область>/<Subject>Tests.cs`, переиспользуемые хелперы —
  в `Infrastructure/`.
* Namespace зеркалит путь, как и в игровом проекте (см. [Соглашения по написанию кода](Code-style.md)).
* Имя метода — `<Что>_<Ожидание>`: `Links_PointToExistingFiles`, `File_UsesLineFeedOnly`.
* Путь к корню репозитория берётся из `RepositoryPaths`, а не собирается вручную: он зашит в сборку
  через `AssemblyMetadata` в `.csproj`, потому что рабочий каталог теста — это `bin/<config>/<tfm>/`.

## Что покрыто сейчас

Только документация — тесты в `Tests/NeonWarfare.Tests/Docs/`. Они проверяют, что ссылки и якоря
внутри `Docs/**/*.md` и `README.md` никуда не протухли, что каждый файл `Docs/` слинкован из
`README.md` и содержит единообразный обратный якорь на него, и что формат файлов соответствует
`.editorconfig`. `CLAUDE.md` не сканируется: в нём намеренно нет markdown-ссылок.

## Что планируется покрыть

Ничего из перечисленного пока не реализовано — это дорожная карта, а не описание существующего.

**Локализация.** Все ключи из `Services.I18N.Tr(KEY)` присутствуют во всех трёх файлах
`Assets/Locales/*.po`; нет осиротевших ключей, которых нет в коде; `messages.pot` не отстал от кода.
Все три файла в `Assets/Locales/` имеют одинаковый набор ключей
Правила — в [Локализации](Localization.md).

**Соглашения кода, проверяемые статически.** Namespace совпадает с путём файла; рядом с каждой
`.tscn` лежит одноимённый `.cs`; у каждой публичной RPC-обёртки есть приватная пара `*Rpc`; в коде
нет `GetMultiplayer().IsServer()` вместо хелперов `Net.*`.
Это ровно те ошибки, которые компилятор не ловит, — см.
[Соглашения по написанию кода](Code-style.md).

**Чистая логика без Godot.** Разбор аргументов из `Scripts/Content/CmdArgs/`
([Параметры командной строки](Cli-args.md)), чат-команды `ICommandProcessor`
([Чат и команды](Arch/Chat-and-commands.md)), математика статов и статус-эффектов
([Сущности](Arch/Entities.md)) — по мере вынесения логики из нод в тестируемые классы.

**Синхронизация окружения.** `Properties/launchSettings.json` и `.run/*.run.xml` соответствуют
таблицам в [Быстром старте](Quick-start.md) — этот инвариант там записан, но никем не проверяется.

**CI.** Прогон `dotnet test` на каждый push. Сейчас CI в репозитории нет вообще.

## Чего здесь не будет

Интеграционных тестов, поднимающих Godot (headless-запуск, проверка дерева сцен, сетевые тесты
сервер + клиент). Они требуют другого инструмента — движок должен запускать тесты сам, изнутри
процесса. Если такие тесты понадобятся, это отдельное решение (gdUnit4 или аналог) и отдельный
проект, а не расширение `NeonWarfare.Tests`. Сетевые сценарии по-прежнему проверяются вручную:
сервер плюс минимум один клиент, см. [Быстрый старт](Quick-start.md).
